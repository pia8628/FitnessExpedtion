## Context
現有 MVP 已有基礎 UI/流程，但仍缺少關鍵能力（遊戲建立/進入、事件觸發邏輯、死亡/懲罰、BOSS/地圖一致性）。目前程式主體在 `program/`，Streamlit 多頁 UI + gspread 連接 Google Sheet。需求新增以「先進入遊戲才能看到內容」為原則，並將事件分成「被動影響」與「任務式事件」兩類，HP 歸零採固定規則。

## Goals / Non-Goals

**Goals:**
- 新增「遊戲創建/進入」流程，未進入前不顯示遊戲內容。
- 事件系統區分「被動影響」與「任務式事件」，並能在流程中正確觸發與記錄。
- HP 歸零與懲罰流程固定化，並且可被完整追蹤與復原。
- BOSS 週結算與地圖進度一致，支援重玩地圖與週數歸 1。

**Non-Goals:**
- 不改動整體技術架構（仍為 Streamlit + Google Sheet）。
- 不新增身份驗證/權限系統。
- 不做非 MVP 的視覺分享或商業化功能。

## Decisions
- **進入門檻與內容顯示**
  - 決定：新增「進入遊戲」狀態控管，未進入時只看到進入/創建頁。
  - 原因：符合使用者需求，避免直接暴露遊戲中資料。
  - 替代方案：直接顯示 Dashboard 並在其中彈出提示；但會讓資料狀態混雜，操作流程不清楚。

- **事件分層：被動影響 vs 任務式事件**
  - 決定：將事件分為兩類，並在邏輯中分別處理。
    - 被動影響：週開始立即生效（例：全員 MP +2）。
    - 任務式事件：有達成條件，達成時觸發（例：本週第一位擊敗怪物的玩家 EXP +1）。
  - 原因：符合既有規則語意，降低事件判定混亂。
  - 替代方案：全部當作通用事件條件引擎；但 MVP 容易過度設計。

- **HP 歸零固定懲罰流程**
  - 決定：固定規則（例如：觸發懲罰事件、或連續兩週 MP 歸零），並記錄懲罰來源。
  - 原因：簡化玩家理解與測試流程。
  - 替代方案：依事件或職業產生不同懲罰；但規則過多且尚未定義。

- **BOSS/地圖進度一致性**
  - 決定：BOSS 結算後必須選擇前進或重玩；重玩地圖則週數歸 1 並重置進度。
  - 原因：符合既有設計紀錄，並避免週數/地圖不同步。
  - 替代方案：重玩維持週數累積；會使地圖進度判斷複雜且易出錯。

## Risks / Trade-offs
- [事件觸發點過多造成重複觸發] → 將觸發點集中於特定流程（週初始化、任務完成/失敗、技能使用）並寫入紀錄防重複。
- [HP 歸零懲罰影響流程理解] → 明確在 UI 顯示懲罰原因與剩餘週數。
- [BOSS/地圖重玩週數歸 1 導致歷史紀錄混亂] → 紀錄中保留地圖與回合欄位，重玩時新增地圖進度序號。

## Migration Plan
- 先新增進入/創建頁與狀態切換，確保可進入遊戲。
- 補齊事件分類與觸發點，寫入日誌。
- 完成 HP 歸零與懲罰流程，補齊 UI 顯示。
- 修正 BOSS/地圖週結算與重玩流程，確保地圖/週數一致。
- 回歸測試：抽事件/怪物、任務完成/失敗、事件觸發、BOSS 結算。

## Open Questions
- HP 歸零懲罰固定為「連續兩週 MP 歸零」。
- 任務式事件需顯示在任務列表中，並與怪物任務分開區塊。
- 進入/創建流程僅使用角色選擇，不加入密碼。
